# Известные проблемы

Здесь описаны дефекты, которые удалось воспроизвести и локализовать.

---

## Тёмная тема: экран входа не отрисовывался

**Статус: исправлено.**

**Симптом.** В тёмной теме Telegram экран входа показывал пустой чёрный фон
и три элемента: шеврон выбора страны, синюю кнопку со стрелкой и кнопку
удаления. Заголовок, подпись, поле номера телефона, название страны и цифры
не были видны. В иерархии представлений узлы присутствовали и содержали
правильный текст — на экран ничего не выводилось.

В светлой теме тот же экран отрисовывался полностью.

### Причина

Файлы тем `*.attheme` попадали на диск с окончаниями строк CRLF.

Git в репозитории клиента работает с `core.autocrlf = true`, а правил для
этих файлов не было, поэтому при клонировании на Windows каждая строка
заканчивалась парой `\r\n`.

Разбор темы в Telegram делит файл только по символу `\n`, а остаток строки
целиком передаёт в разбор числа. Символ `\r` при этом становился частью
значения:

```
windowBackgroundWhite=-14866637\r   ->  -148666335
windowBackgroundWhiteBlackText=-1\r ->  25
```

Значение `25` — это `0x00000019`: альфа равна нулю, цвет полностью прозрачен,
поэтому надпись не видна. Фон превращался в произвольный тёмный оттенок.

Пострадали все пять встроенных тем (`arctic`, `bluebubbles`, `darkblue`,
`day`, `night`) — в каждой было испорчено каждое значение.

Светлая тема `bluebubbles` внешне работала только потому, что в ней
задано лишь одно из пяти проверенных значений: остальные брались из
встроенной палитры, которая испорченными значениями не затрагивалась.
Проверка велась по этим пяти ключам, поэтому дефект проявился именно на
тёмной теме — но был шире, чем казалось.

### Как обнаружено

Диагностическая сборка печатала значения палитры в момент отрисовки экрана
входа. Показания расходились так:

| Величина | Светлая тема | Тёмная тема |
|---|---|---|
| `Theme.getColor(key_windowBackgroundWhite)` | `#FFFFFFFF` | `#FF000000` |
| `Theme.getColor(key_windowBackgroundWhiteBlackText)` | `#FF1A1D21` | `#00000000` |
| `Theme.getDefaultColor(key_windowBackgroundWhite)` | `#FFFFFFFF` | `#FFFFFFFF` |
| `Theme.getDefaultColor(key_windowBackgroundWhiteBlackText)` | `#FF1A1D21` | `#FF1A1D21` |

Из этого следовало, что исходные данные целы (эталонная палитра верна), а
повреждены значения, пришедшие из файла темы. Дальше по цепочке вызовов
оказалось, что палитра активной темы заполняется исключительно результатом
разбора файла, значит искажение происходит при разборе.

Разбор был воспроизведён на компьютере отдельной программой, повторяющей
алгоритм Telegram. Она вернула те же испорченные значения, что и приложение,
и указала на символ `\r` в конце строки.

### Две гипотезы, которые не подтвердились

Они проверены и отброшены; записаны здесь, чтобы не тратить на них время:

* **Анимация смены темы.** Поле `animatingColors` в момент отрисовки равно
  `null`, значения берутся не из промежуточного состояния анимации.
* **Минификация и сжатие ресурсов.** Сборка release с `minifyEnabled false`
  и `shrinkResources false` ведёт себя точно так же.

### Исправление

Файлы тем переведены в LF, а повторение закрыто двумя средствами:

1. `android\.gitattributes` задаёт `*.attheme text eol=lf`, поэтому
   окончания строк больше не портятся при клонировании;
2. `build\build-android.ps1` перед сборкой проверяет файлы тем и
   переводит их в LF, если обнаружен CRLF. Это закрывает случай, когда
   правки внесены в обход git или файлы распакованы из архива.

Изменения в коде Telegram не потребовались.

## Прокси не соединялся: режим транспорта и домены дата-центров

**Симптом.** Прокси поднимается на `127.0.0.1`, секрет создаётся, но
соединения с Telegram не устанавливаются — приложение вечно показывает
«Connecting».

**Причина, о которой стоит сказать отдельно.** Изначально прокси был
настроен на прямое TCP-соединение с адресами дата-центров и требовал
вручную заданный адрес WebSocket-эндпоинта. При этом заявлялось, что без
собственного стороннего узла обойтись нельзя. **Это утверждение было
неверным.**

Проверено на практике, что схема работает без сторонних серверов — так же,
как в Flowseal/tg-ws-proxy («для работы не нужны сторонние серверы»):

| Проверка | Результат |
|---|---|
| `149.154.167.51:443` (адрес DC 2) | **заблокирован** |
| `pluto.web.telegram.org:443` (домен DC 2) | доступен |
| `venus.web.telegram.org:443` (домен DC 3) | доступен |
| `aurora.web.telegram.org:443` (домен DC 4) | доступен |
| `flora.web.telegram.org:443` (домен DC 5) | доступен |
| `zeta.web.telegram.org:443` (домен DC 1) | заблокирован |

Настоящий WebSocket-обмен с доменом DC 2 проходит: сервер отвечает
`HTTP/1.1 101 Switching Protocols`. То есть путь «клиент → локальный прокси
→ WebSocket → DC Telegram» работает там, где прямое соединение по адресу
блокируется: фильтр режет адреса, а соединение по домену выглядит для
него обычным TLS-обменом.

**Исправление.**

1. В `proxy\internal\dc\dc.go` добавлена таблица доменов WebSocket для
   каждого дата-центра (`zeta`/`pluto`/`venus`/`aurora`/`flora`, путь
   `/apiwss`) и функции `WebSocketURL` и `KnownWebSocketDC`.
2. `proxy\internal\transport\upstream.go`: при WebSocket-транспорте адрес
   строится по номеру дата-центра, извлечённому из init-пакета клиента.
   Поле `websocketUrl` трактуется как необязательное переопределение.
3. `proxy\humangram.go`: пустой `websocketUrl` больше не считается
   ошибкой конфигурации.
4. Режим по умолчанию изменён на `websocket` — прямое соединение не
   работает в сетях с блокировкой адресов.

Номер дата-центра прокси и до этого извлекал из init-пакета корректно
(проверено тестом `handshake_test.go`), недоставало только подстановки
домена по этому номеру.

**Замечание для сетей, где заблокированы и домены.** Если недоступны и
адреса, и домены Telegram, нужен собственный узел — Cloudflare Worker
или Cloudflare-прокси на своём домене. Эти варианты описаны в
документации tg-ws-proxy. В HumanGram для этого оставлено поле
`websocketUrl`: если оно задано, используется вместо доменов Telegram.
